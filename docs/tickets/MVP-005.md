## Implemented scope

Products belong to database categories, have active/inactive visibility, accept
validated images through configured storage, and enforce product/variant model
permissions. Product attribution and auditing use the merged MVP-003 foundation.
Prices and stock are MVP-006; customer-facing browse/detail UX is MVP-007.
The existing navy/emerald dashboard and corrected category table layout are the
visual baseline. The supplied index.html is a design reference, not authority
to copy demo-only behavior or expand this ticket into pricing/stock management.

User confirmed flexible variants with required unique SKUs, permanent deletion,
and JPEG/PNG/WebP uploads up to 8 MB. SKU case/outer whitespace normalize; database
constraints enforce uniqueness across products. Attribute keys normalize and
values must be text. A new product requires at least one variant. Independent
categories can contain products; parent categories cannot be selected.

Product deletion uses the existing confirmation popup and cascades variants/photos;
Django additionally checks variant deletion permission. Categories with products
are protected from deletion. Uploaded images use random storage names, validated
actual formats, private admin access, and visibility-checked public access. File
cleanup happens on successful commit. Product/variant/photo attribution and audit
reuse MVP-003. Photo permissions follow product edit permissions; variant actions
have their own role grants. Minimal `/products/` output verifies visibility;
full customer browse/detail styling remains MVP-007.

## QA scenarios prepared before implementation

- Super Admin and appropriately granted workers can create/edit products and
  variants; view-only, unrelated-role, anonymous and inactive accounts cannot
  mutate them, including direct requests and inline formset submissions.
- Product/category links validate, including independent categories, inactive
  categories and inactive ancestors. Public visibility must not disclose
  inactive products, inactive variants or products beneath inactive ancestors.
- SKU uniqueness handles duplicate creation/edit, case/outer whitespace and
  database-level concurrent writes according to the confirmed SKU policy.
- Uploads validate actual image contents, supported formats and size; corrupt,
  renamed non-images, oversize payloads and path traversal filenames fail safely.
  Stored uploads use configured media storage and permission-checked access.
- Creator/editor and creation/update times cannot be forged. Product/variant
  changes generate audit records with no credentials or secrets.
- Archive/deletion and category deletion behavior follow the confirmed policy,
  preserve history, and clean up images only after successful commits where
  applicable. Validation failures must not silently remove existing photos.
- Lists/forms handle empty data, long names, filter counts and pagination;
  desktop/mobile rendering and keyboard interaction require a connected browser
  and independent QA of the exact candidate SHA.

Independent review and visual QA remain pending.
